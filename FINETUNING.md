## 1. How It All Fits Together

```
Your 1,108 ChromaDB chunks
        │
        ▼
┌─────────────────────┐
│  prepare_dataset.py │  Asks qwen2.5:7b to write Q&A pairs for each chunk
│  (Phase 1)          │  Saves to train.jsonl / val.jsonl
└─────────────────────┘
        │
        ▼
┌─────────────────────┐
│     train.py        │  Converts model to MLX 4-bit format (once)
│  (Phase 3)          │  Runs LoRA fine-tuning via mlx-lm
│                     │  Saves adapter to finetune/adapters/
└─────────────────────┘
        │
        ▼
┌─────────────────────┐
│  merge_adapter.py   │  Folds LoRA weights into base model
│  (Phase 4)          │  Saves merged fp16 model to finetune/merged_model/
└─────────────────────┘
        │
        ▼
┌─────────────────────┐
│  convert_gguf.sh    │  Converts merged model → fp16 GGUF → Q4_K_M GGUF
│  (Phase 6)          │  Uses llama.cpp (Metal-accelerated on M1)
└─────────────────────┘
        │
        ▼
┌─────────────────────┐
│  deploy_ollama.sh   │  ollama create qwen2.5-salesforce
│  (Phase 7)          │  Runs smoke test
└─────────────────────┘
        │
        ▼
┌─────────────────────────────────────────────────────┐
│  server.py  (unchanged)                             │
│    RAG pipeline: ChromaDB → context → fine-tuned    │
│    model → answer → FastAPI response                │
└─────────────────────────────────────────────────────┘
```

**Key principle:** Fine-tuning teaches the model *how* to answer Salesforce questions (vocabulary, style, formatting). The RAG pipeline continues to provide the *what* (specific document content per query). They work together — the fine-tuned model is simply a drop-in replacement in `config.yaml`.

## Phase 1 — Generate the Training Dataset

This step reads every chunk from ChromaDB and asks your local `qwen2.5:7b` to write Q&A pairs for each one. The output is `train.jsonl` and `val.jsonl`.

> **Make sure Ollama is running before you start:**
> ```bash
> ollama list   # should show qwen2.5:7b
> ```

### First run

```bash
python finetune/preprocessing/prepare_dataset.py generate \
    --n-pairs 3 \
    --max-chunks 200
```

| Flag | Value | Meaning |
|---|---|---|
| `--n-pairs 3` | 3 | Generate 3 Q&A pairs per chunk |
| `--max-chunks 200` | 200 | Process 200 chunks this session |

**Expected time:** ~50 minutes  
**Expected output at the end:**
```
Generated 521 examples (17 chunks skipped).
  Wrote 469 → train.jsonl
  Wrote 52  → val.jsonl

Progress saved → generation_progress.json
  Total train examples so far : 469
  Total val examples so far   : 52

  908 chunks remaining.
  Tomorrow, run:
    python finetune/preprocessing/prepare_dataset.py generate --n-pairs 3 --max-chunks 200 --resume
```

### Resuming the next day

The script tells you the exact command. Every subsequent day:

```bash
python finetune/preprocessing/prepare_dataset.py generate \
    --n-pairs 3 \
    --max-chunks 200 \
    --resume
```

`--resume` reads `generation_progress.json` and automatically starts from where you left off. **No math required.**

### Check progress at any time

```bash
python finetune/preprocessing/prepare_dataset.py status
```

```
==================================================
Dataset generation progress
==================================================
  Chunks processed : 400 / 1108
  Chunks remaining : 708
  Total examples   : 1,043
  Train examples   : 937
  Val examples     : 106
  Batches run      : 2
    Batch 1: chunks 0-199   → 521 examples  (2025-07-24 09:15)
    Batch 2: chunks 200-399 → 522 examples  (2025-07-25 09:30)

```

### Generation schedule for all 1,108 chunks

| Day | Chunks | Est. time | Command |
|---|---|---|---|
| 1 | 0–199 | ~50 min | `generate --max-chunks 200` |
| 2 | 200–399 | ~50 min | `generate --max-chunks 200 --resume` |
| 3 | 400–599 | ~50 min | same |
| 4 | 600–799 | ~50 min | same |
| 5 | 800–999 | ~50 min | same |
| 6 | 1000–1107 | ~27 min | same |

> **You don't have to wait for the full dataset to start training.**  
> Even 469 examples (Day 1 only) is enough for a first training run to verify the pipeline works end to end. Train on Day 1 results, then retrain with more data later.

### Alternative: use seed examples only (instant)

If you want to test the full pipeline right now without waiting 50 minutes:

```bash
python finetune/preprocessing/prepare_dataset.py convert
```

This converts the 10 hand-crafted examples in `finetune/dataset/raw/salesforce_examples.jsonl` into training format. The model won't improve much with 10 examples, but it lets you verify every step works before committing time to dataset generation.

## Phase 3 — Run Training

One command runs everything: model download, MLX conversion, and training.

```bash
python finetune/training/train.py
```

### What happens internally

```
[Step 1/4] Converting Qwen/Qwen2.5-7B-Instruct → MLX 4-bit …
           Downloads ~14 GB from HuggingFace (first run only, cached after)
           Converts to 4-bit MLX format → finetune/mlx_model/
           Time: ~15 minutes (download) + ~5 minutes (conversion)

[Step 2/4] Data directory ready
           Creates valid.jsonl symlink (mlx-lm requires this exact filename)

[Step 3/4] Writing training config → finetune/training/lora_config.yaml
           Calculates total iterations from dataset size × epochs

[Step 4/4] Starting mlx-lm LoRA training …
           Prints loss every 10 steps
           Saves adapter checkpoint every 100 steps → finetune/adapters/
```

### Training output to watch

```
Iter 1:   Train loss 2.450, It/sec 0.42, Tokens/sec 856
Iter 10:  Train loss 1.923, It/sec 0.45, Tokens/sec 912
Iter 50:  Train loss 1.421, It/sec 0.44, Tokens/sec 895
Iter 100: Val loss 1.380, Val took 9.1s
Iter 200: Train loss 1.102, It/sec 0.44, Tokens/sec 891
Iter 360: Train loss 0.821, It/sec 0.44, Tokens/sec 895
```

Train loss should drop steadily from ~2.5 towards ~0.8. If val loss stops improving but train loss keeps dropping, the model is overfitting — reduce `--epochs` next time.

### Expected training times (M1 Max)

| Dataset size | Epochs | Total steps | Time |
|---|---|---|---|
| 9 examples (seed only) | 3 | 6 | < 1 minute |
| 469 examples (Day 1) | 3 | ~350 | ~2.5 hours |
| 937 examples (Day 1+2) | 3 | ~700 | ~4.5 hours |
| ~3,000 examples (full) | 3 | ~2,250 | ~6 hours |

### CLI options

```bash
# Train with more epochs (small dataset)
python finetune/training/train.py --epochs 5

# Higher rank for richer adaptation (needs more memory)
python finetune/training/train.py --rank 16 --scale 10

# Train in fp16 instead of 4-bit (uses ~21 GB, slightly higher quality)
python finetune/training/train.py --no-quantize

# Skip model conversion (if mlx_model/ already exists)
python finetune/training/train.py --skip-convert
```

### Resuming after interruption

Training checkpoints are saved every 100 steps to `finetune/adapters/qwen2.5-salesforce/`. If you press Ctrl-C or the machine sleeps, just re-run:

```bash
python finetune/training/train.py --skip-convert
```

mlx-lm automatically finds and resumes from the latest checkpoint.

### Monitor memory while training

Open a second terminal and run:

```bash
sudo powermetrics --samplers gpu_power -n 10 -i 2000 | grep -E "GPU|ANE"
```

You should see GPU active power ~20–40 W. If memory pressure turns red in Activity Monitor, reduce `--batch-size` to 2.

## Phase 4 — Merge the Adapter

After training, you have a small adapter (~50–100 MB) that must be folded into the base model before GGUF conversion. This step produces a single complete model in HuggingFace safetensors format.

```bash
python finetune/scripts/merge_adapter.py
```

**What happens:**
- Loads the MLX base model and the LoRA adapter
- Computes `W_merged = W_base + scale × (B × A)` for every adapted layer
- Dequantises from 4-bit back to fp16 (required for llama.cpp)
- Saves to `finetune/merged_model/` as standard safetensors shards

**Expected time:** 3–5 minutes  
**Expected output:**
```
Running mlx_lm fuse (this takes 2-5 minutes) …
  Safetensors : 4 shard(s), 13.8 GB total
  config.json : found
Merge complete.
  Next step → run: bash finetune/scripts/convert_gguf.sh
```

**Why not use `--export-gguf`?**  
`mlx_lm fuse` has a `--export-gguf` flag but it only supports `llama`, `mixtral`, and `mistral` model types. Qwen2.5 uses model type `qwen2`, which raises `ValueError`. We use llama.cpp for the GGUF step instead.

## Phase 5 — Build llama.cpp (one-time)

llama.cpp is used only for the GGUF quantisation step. You build it once and reuse it forever.

```bash
git clone https://github.com/ggerganov/llama.cpp ~/llama.cpp
cd ~/llama.cpp
cmake -B build -DGGML_METAL=ON
cmake --build build -j10
pip install -r requirements.txt
```

| Flag | Meaning |
|---|---|
| `-DGGML_METAL=ON` | Use your M1 GPU for fast quantisation |
| `-j10` | Use all 10 CPU cores to compile |

**Expected build time:** 3–5 minutes  

**Verify it built correctly:**
```bash
~/llama.cpp/build/bin/llama-quantize --help 2>&1 | head -2
```
Expected: `usage: llama-quantize [--help] [--allow-requantize] ...`

> **You only need to do this once.** Future retraining runs skip this phase entirely.

## Phase 6 — Convert to GGUF

Converts the merged HuggingFace model to the binary format Ollama uses.

```bash
cd /Users/test/LocalOllamaLLM/salesforce-rag
bash finetune/scripts/convert_gguf.sh
```

Default quantisation is `Q4_K_M`. Options:

```bash
bash finetune/scripts/convert_gguf.sh Q4_K_M   # 4-bit mixed, ~4.1 GB  (default)
bash finetune/scripts/convert_gguf.sh Q5_K_M   # 5-bit mixed, ~4.8 GB  (better quality)
bash finetune/scripts/convert_gguf.sh Q8_0     # 8-bit,       ~7.2 GB  (near lossless)
```

### What happens internally

```
[1/2] Converting safetensors → fp16 GGUF …
      Reads finetune/merged_model/*.safetensors
      Writes finetune/gguf/qwen2.5-salesforce.fp16.gguf  (~14 GB)

[2/2] Quantising to Q4_K_M …
      Reads the fp16 GGUF
      Writes finetune/gguf/qwen2.5-salesforce-Q4_K_M.gguf  (~4 GB)

Delete intermediate fp16 GGUF to save space? [Y/n]  → press Y
```

**Expected time:** ~8 minutes total on M1 Max with Metal  
**Final file:** `finetune/gguf/qwen2.5-salesforce-Q4_K_M.gguf`

## Multi-Day Dataset Generation Schedule

The generation step is the only one that requires you to be present daily. All other phases run unattended once started.

```
Day 1:  generate --max-chunks 200          (~50 min, sit and watch)
Day 2:  generate --max-chunks 200 --resume (~50 min)
Day 3:  generate --max-chunks 200 --resume (~50 min)
Day 4:  generate --max-chunks 200 --resume (~50 min)
Day 5:  generate --max-chunks 200 --resume (~50 min)
Day 6:  generate --max-chunks 200 --resume (~27 min, last batch)

        ↓  all 1,108 chunks done  ↓

Day 6 afternoon (or Day 7):
  validate → train (leave overnight) → merge → convert → deploy → done
```

> **Can I run the full 1,108 chunks in one session?**  
> Yes — just omit `--max-chunks`. The command will run for ~5 hours unattended. Make sure your Mac is plugged in and set to never sleep during training in System Settings → Battery → Prevent automatic sleeping.

## Hyperparameter Reference

Defined in `finetune/training/config.py`. Change defaults there or override via CLI flags.

| Parameter | Default | CLI flag | Notes |
|---|---|---|---|
| LoRA rank | 8 | `--rank` | 4=minimal, 8=recommended, 16=rich |
| LoRA scale | 10.0 | `--scale` | ≈ alpha/r in HuggingFace terms |
| LoRA dropout | 0.05 | `--dropout` | Increase to 0.1 if overfitting |
| Layers with LoRA | 16 | `--num-layers` | -1 = all 28 layers |
| Epochs | 3 | `--epochs` | 5 for small datasets (<500 examples) |
| Batch size | 4 | `--batch-size` | Reduce to 2 if memory pressure is high |
| Gradient accumulation | 4 | `--grad-accum` | Effective batch = 4×4 = 16 |
| Learning rate | 2e-5 | `--lr` | 1e-5 conservative, 5e-5 aggressive |
| Max sequence length | 2048 | `--seq-len` | Covers 99% of Salesforce Q&A |
| Quantisation | 4-bit | `--no-quantize` | fp16 needs ~21 GB free |

## Troubleshooting

### "ChromaDB is empty — run ingest.py first"
The vector database is not populated. Run `python ingest.py` first to index your Salesforce documents.

### "mlx_model/ does not exist" during merge
Run training first. The model conversion happens automatically as Step 1 of `train.py`.

### Ollama call times out during dataset generation
```bash
# Check Ollama is running
ollama list

# Increase timeout in config.yaml if needed
# timeout: 300  (default is 180)
```

### Training loss spikes after a checkpoint resume
This is normal for the first few steps after resuming — the optimizer state warms up again. It stabilises within 20 steps.

### "ValueError: Model type qwen2 not supported" during fuse
Do **not** pass `--export-gguf` to `mlx_lm fuse`. This is handled by `convert_gguf.sh` using llama.cpp instead. The `merge_adapter.py` script does not use that flag.

### GGUF conversion fails with "convert_hf_to_gguf.py not found"
llama.cpp has not been cloned yet. Run Phase 5 first.

### Out of memory during training
```bash
# Reduce batch size
python finetune/training/train.py --batch-size 2

# Or reduce sequence length
python finetune/training/train.py --batch-size 2 --seq-len 1024

# Or reduce number of adapted layers
python finetune/training/train.py --num-layers 8
```

### Fine-tuned model gives worse answers than the base model
- Dataset is too small (< 200 examples) — generate more chunks
- Learning rate is too high — try `--lr 1e-5`
- Model overfit — reduce `--epochs` to 2 or increase `--dropout` to 0.1
- Re-run `python finetune/evaluation/evaluate.py` to compare metrics

### To go back to the original model
```bash
# Edit config.yaml
llm_model: "qwen2.5:7b"   # revert this line

# Restart server
python server.py
```

No data is deleted. Both models coexist in Ollama and you can switch instantly by changing `config.yaml`.
